# Firebase Authentication integration

Firebase remains responsible only for Android Google Sign-In in the existing project `apartment-booking-manage-2d218`, on Spark. The existing native Auth plugin, Google Credential Manager, Android/OAuth configuration, package ID and APK signing identity are unchanged. No Functions, Firestore, Cloud Storage, Blaze or Google service-account private key is required by the active backend.

The server is now Cloudflare Workers + D1. See [access.md](access.md) for the access policy and [secure-access-setup.md](secure-access-setup.md) for the exact manual setup, free-plan quotas, credentials and offline limits. The previous Firebase Functions deployment path has been removed rather than left as an accidental billing dependency.

The Worker validates Firebase ID tokens using JOSE and Google's fixed public certificate endpoint. It checks RS256/signature, issuer, audience/project, expiry, subject, issue/authentication times and Google provider. An Auth REST end-user lookup with the same ID token checks the account and revocation timestamp without an administrative service account. The Worker API key must allow Firebase Authentication/Identity Toolkit requests from the backend; missing/restricted configuration or Google quota errors deny new verification with 503. No token or account-lookup response is logged or cached. Verify actual Auth REST behavior in restricted integration testing before publication; local tests use fictional JWTs and a mock Google service, not real Firebase users.

`src/secure-access.js` remains the Android composition path and `BookingAccessPlugin` retains its signed-proof and Keystore boundary. `src/firebase-access.js` is the earlier short-lease transport contract kept for regression tests, not the persistent Android entitlement implementation. The Firebase bridge must expose SDK-issued Firebase ID tokens, not raw Google OAuth access tokens. BASIC never waits for login/network.

No cloud resources have been created or services published. The actual backend URL and Android public-key pin remain unset. Google Sign-In and the complete signed-license lifecycle still require physical-device and configured-service verification before being described as operational.

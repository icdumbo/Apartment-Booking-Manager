# BASIC / TRIAL / PREMIUM foundation

`src/access.js` owns entitlement persistence and policy. Existing business storage remains version 1 and is not migrated or truncated. A separate versioned key records explicit trial activation and the highest observed timestamp. TRIAL lasts exactly 15 × 24 hours, including offline time; expiry is rechecked on resume, periodic state checks and every write. BASIC permits managing the first three apartments in stored order; all additional apartments/reservations can be viewed read-only. Deleting an active apartment makes the next stored apartment manageable. Reassignment into read-only apartments is blocked. An expired open editor cannot bypass write guards.

The first-use RO/EN notice explains expiry, free BASIC, one-time permanent PREMIUM, data retention and planned ads in all tiers. Activation is explicit; no billing or ad SDK is installed. `accessPolicy` already supports PREMIUM; the unavailable Billing adapter exposes purchase/restore integration points. No local premium toggle is accepted. A future verified Google Play purchase provider must resolve permanent entitlement before PREMIUM can be activated.

This offline foundation is not tamper-resistant: clearing app storage or manipulating local records/device time can affect trial enforcement. Highest observed time prevents simple clock rollback after expiry has been observed, but is not a trusted time source. Corrupt/unavailable entitlement storage fails to BASIC without overwriting it or business data. Add trusted purchase verification and reconcile purchase/restoration/lifecycle results during the Billing phase.

Calendar, responsive CSS, half-day geometry, application ID and signing configuration are unchanged. Nothing is deployed from the working branch.

## Trusted PREMIUM verification contract

`createPremiumProvider({verifyAccess, getAuthenticatedSubject, clock})` is the single integration boundary for future trusted rights verification. The existing app still uses the unavailable Billing adapter: no production account is granted access by this change. There is no activation code, owner email comparison, local PREMIUM flag or purchase simulator.

After successful verification, the adapter must return `{subject, source, permanent: true, verifiedUntil}`. `source` is `GOOGLE_PLAY_PURCHASE` for a one-time purchase or `OWNER_GRANT` for the owner's complimentary lifetime access. `subject` is an opaque authenticated account ID, never an email entered by the user. `verifiedUntil` is the verification lease expiration in epoch milliseconds, not the expiration of the permanent license. This normalized object is a contract for already verified results, not a proof format: merely matching its shape does not authenticate it.

`verifyAccess` must be supplied by trusted integration code that validates the authenticated server response/proof; it must never read editable local entitlement data or simply trust arbitrary JSON. `getAuthenticatedSubject` must read the validated authentication session. No transport, cryptographic verifier, login, backend or Billing SDK is implemented yet. Do not connect these hooks to unverified inputs.

The provider retains grants only in memory, returns defensive copies and checks the session binding and verification deadline at every read. Refresh clears the old grant before verification. Missing, rejected, expired or failed verification falls back to the existing TRIAL/BASIC rules, preserving all data. Logout must call `clear()`; session changes also invalidate access on read. Generation checks prevent pending responses from restoring a cleared grant or overriding a newer refresh. A restart requires fresh trusted verification; persistent offline PREMIUM proof is deliberately not implemented. The trial's offline behavior remains unchanged.

## Backend requirements for the next phase (not implemented)

- Authenticate the account with a validated identity-provider session/token; derive its stable subject on the server, never trust a client-supplied subject alone. Define secure account linking so purchases and restoration remain associated with the correct user.
- Store the sole owner's subject in protected server configuration/records. Only privileged administration may issue that one non-transferable, permanent complimentary grant; normal users, family members and other accounts must not self-assign it. No owner identity or secret belongs in the app/repository. Audit issuance/revocation and keep administrative credentials server-side.
- For purchases, verify the purchase token server-side with Google Play, validate application/product, completed purchase state and account association, and enforce purchase-token uniqueness. Handle restoration, required acknowledgement, refunds and revocations. Product configuration and current Billing requirements must be checked when that phase starts.
- Resolve both sources to the same permanent PREMIUM policy. Return only minimal account-bound rights over an authenticated secure channel; deny unauthorized requests. Define refresh, sign-out, revocation and network-failure handling. Feed refreshed results back into the app access service/UI without modifying calendar/business records.
- If persistent offline PREMIUM is later required, design signed, short-lived, account/application/audience-bound leases with server time, expiry, issuer/key validation, replay protections and revocation policy. Keep signing keys exclusively on the server; public verification keys are not secrets. Local flags and the device clock alone cannot prove ownership or permanent access.

Until that phase is authorized and implemented, owner access and paid access are recognized only through injected trusted test adapters, not available for real activation. No infrastructure is provisioned and no real purchase or advertisement is enabled.
